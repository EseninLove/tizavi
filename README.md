# Tizavi Shop

Telegram Mini App продуктового магазина. React, Vite, TypeScript, PostgreSQL и Vercel Functions.

## Запуск и проверки

```sh
npm ci
npm run dev
npm run typecheck
npm test
npm run build
```

`npm run dev` запускает интерфейс на порту 3000. Для настоящих API нужен Vercel development environment с переменными из `.env.example`. Без БД и настроенных внешних сервисов каталог и расчёт адресов не имитируют успешные ответы. Не подключайте рабочую БД к автоматическим тестам: они используют временный PostgreSQL в памяти (PGlite), а запросы к агрегаторам и DaData заменяют локальными ответами.

## Инициализация и обновление базы

Войдите в `/admin` с `ADMIN_KEY`, откройте «Настройки» и инициализируйте БД. Для существующей базы миграция `db/002-commerce.sql` применяется автоматически при первом обращении к новым API. Она выполняется один раз в транзакции под блокировкой PostgreSQL. SQL-файл включён в сборку серверных функций через `vercel.json`.

Существующие заказы не удаляются. Старые записи не содержат доказательства оплаты, поэтому получают `payment_status=unverified` («Оплата требует проверки»), сохраняя прежний статус доставки. Для них нельзя автоматически начать новую оплату или отправить заказ. Проверьте их по данным прежнего провайдера. Старые подписки сохранены; данная миграция не доказывает законность их прошлой активации.

Категории сохраняют прежние стабильные slug. Переименование меняет только отображаемое название. Новые категории получают неизменяемый случайный slug. Категорию с товарами удалить нельзя: сначала перенесите товары.

## Подключение оплаты

Первый набор адаптеров: **ЮKassa и Т-Банк**. Stars и прежний `/api/create-invoice`, принимающий сумму покупателя, отключены. Оба адаптера используют внешнюю страницу оплаты картой. Методы оплаты на этой странице зависят от договора и настроек агрегатора.

1. Создайте магазин/терминал у агрегатора и получите его ключи.
2. Задайте `PUBLIC_APP_URL` — HTTPS-адрес опубликованного магазина.
3. Хранение ключей через админку доступно при настроенном серверном `BOT_TOKEN`: из него через HMAC получается отдельный ключ шифрования. Можно заранее задать независимый `PAYMENT_SETTINGS_KEY`: 64 случайных шестнадцатеричных символа (`openssl rand -hex 32`). В зашифрованной записи сохраняется источник защиты, поэтому добавление отдельного ключа не ломает прежние подключения. Не меняйте `BOT_TOKEN` или используемый `PAYMENT_SETTINGS_KEY` без переноса зашифрованных ключей.
4. В `/admin/payments` выберите агрегатор, введите ключи и адрес магазина, сохраните подключение и нажмите «Использовать для оплаты». Этот раздел доступен только `super_admin` и входу владельца через `ADMIN_KEY`.
5. Альтернатива вводу ключей: переменные сервера `YOOKASSA_SHOP_ID` / `YOOKASSA_SECRET_KEY` или `TBANK_TERMINAL_KEY` / `TBANK_PASSWORD`. Они не передаются в браузер. Настройки из админки имеют приоритет.
6. В ЮKassa настройте HTTP-уведомления на `https://ваш-магазин/api/payment-webhook` для `payment.succeeded` и `payment.canceled`. Т-Банк получает этот адрес в `Init`; проверьте настройки HTTP-уведомлений терминала.
7. Проверьте в отдельном тестовом магазине успешную оплату, отмену, задержку уведомления и повторный запрос. Для тестовых платежей ЮKassa нужно явно разрешить тестовый режим; перед рабочими продажами выключите его. Т-Банк должен использовать одностадийный рабочий терминал; адаптер передаёт `PayType=O`.
8. Настройте чеки на стороне агрегатора/подключённой кассы под ваш договор. Автоматическая передача номенклатурного `Receipt` в этой версии не реализована. До рабочего запуска проверьте схему чеков с агрегатором.

Секреты из админки шифруются AES-256-GCM. API возвращает только признак наличия ключей. Переключение активного агрегатора касается новых платежей; для старых сохраняется название их провайдера. Не заменяйте учётную запись магазина у провайдера, пока есть незавершённые платежи: проверка использует текущие ключи этого провайдера.

### Как подтверждается оплата

- Покупатель передаёт только ID товаров и количество. Сервер получает цены/наличие из базы, проверяет количества и адрес, рассчитывает товары и доставку в копейках.
- До оплаты заказ сохраняется как `pending` с `payment_status=pending`. Сервер возвращает рассчитанный состав и сумму, которые покупатель подтверждает перед оплатой.
- Платёж связывается с сохранённым заказом. Для подписки сервер фиксирует цену и количество дней.
- Уведомление агрегатора не считается доказательством само по себе: сервер запрашивает реальный платёж через авторизованный API провайдера и сверяет ID, сумму, валюту и привязку к локальному платежу.
- Только подтверждённый `succeeded`/`CONFIRMED` меняет оплату заказа или продлевает подписку. Повторные подтверждения не начисляют дни и статистику повторно.
- Прямой пользовательский `action=activate` всегда отклоняется. Администратор не может вручную выставить «Оплачен» через API статусов заказа.
- Возврат на `/payment-return` не подтверждает оплату. После возврата в Telegram магазин запрашивает серверный статус. При ошибке проверки или сохранения корзина остаётся.
- Если ответ `Init` Т-Банка потерян, адаптер проверяет существующий OrderId, чтобы не создать повторный платёж. Если URL оплаты не удалось восстановить, магазин открывает проверку состояния; для зависшего неоплаченного платежа понадобится проверка оператором.

Возвраты денежных средств и обработка частичных возвратов — следующий этап; отмена статуса доставки не выполняет банковский возврат.

Документация адаптеров: [ЮKassa](https://yookassa.ru/developers/using-api/webhooks), [Т-Банк: платёжная форма](https://developer.tbank.ru/eacq/scenarios/payments/nonPCI), [Т-Банк: подпись](https://developer.tbank.ru/eacq/intro/developer/token).

## Доставка: Москва и Московская область

В `/admin/delivery` добавьте настоящие склады, координаты, радиус обслуживания, время сборки и часы работы по Москве. Добавьте курьеров и закрепите их за складами. Склады и курьеры можно отключать без удаления.

Настройте базовый тариф, доплату за километр, порог бесплатной доставки, среднюю скорость и коэффициент длины дороги.

Для подсказок улиц и домов, проверки региона и координат подготовлен адаптер **DaData**. Подключение пока не выполнено: задайте `DADATA_TOKEN` в переменных сервера после регистрации сервиса. Инструкция: [подсказки адресов](https://dadata.ru/api/suggest/address/) и [поиск дома по ФИАС](https://dadata.ru/api/find-address/).

Сервер принимает выбранный ID дома, заново получает адрес/координаты, разрешает только регионы 77 и 50 и выбирает ближайший активный склад в радиусе с активным курьером. Координаты покупателя и стоимость доставки не принимаются на доверии из браузера.

**Это предварительная оценка, не автомобильный маршрут:** расстояние между координатами умножается на коэффициент дороги, время рассчитывается по настроенной скорости и времени сборки. Учитывается время открытия склада. Пробки, дорожная сеть, текущая загрузка курьера и назначение конкретного курьера заказу пока не рассчитываются. Интерфейс прямо называет время ориентировочным. Реальные маршруты можно добавить отдельным адаптером позднее.

## Каталог, поиск, рейтинги

Категории открываются в боковом меню, поддерживают фото/значок и сортировку. Поиск раскрывается по кнопке; закрытие очищает запрос. Поддерживаются история запросов на устройстве, синонимы, бренд, небольшие опечатки, цена, наличие и сортировка. Для больших каталогов потребуется серверный поиск с пагинацией.

В товарах администратор задаёт фото, бренд, упаковку, синонимы и участие в сезонном/популярном разделе. Популярность также учитывает подтверждённые неотменённые покупки. Акции определяются старой ценой выше текущей.

Рейтинг — взвешенная средняя оценок магазина (администратор задаёт среднее и количество) и опубликованных реальных оценок покупателей. Источники показаны отдельно в подробной карточке; рейтинг скрывается при отсутствии оценок. Оставить отзыв может только пользователь с подтверждённой покупкой. Один пользователь — одна оценка товара. Изменённый отзыв скрывается до модерации; в `/admin/reviews` можно публиковать/скрывать отзывы.

Повтор заказа в профиле добавляет доступные товары по текущим ценам и сообщает о недоступных позициях. Товары, добавленные после начала оплаты, сохраняются: после подтверждения вычитаются только оплаченные количества.

## Проверки

`npm test` проверяет серверный расчёт, количества, привязку платежа, ближайший доступный склад, московские часы, поиск, прямую поддельную активацию подписки, повторную активацию, подмену суммы, повторную попытку заказа, отмену платежа, повторную оплату, категории и отзывы. SQL выполняется в PostgreSQL PGlite; внешние API заменены контролируемыми ответами. Конкурентные блокировки настоящего PostgreSQL и живые платежи необходимо проверить в тестовом окружении перед публикацией.
